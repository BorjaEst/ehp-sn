# `ehp-sn` CLI

<!-- canonical_package: ehp_sn  authority: canonical  status: draft -->

The `ehp-sn` command-line interface exposes the EHP-SN research lifecycle through a small set of top-level commands.

```text
data → tasks → train → evaluate → analyze → report
```

This documentation defines the intended public CLI contract. A documented command is not considered implemented or validated until its help output and acceptance tests confirm the behavior.

## Usage

```console
ehp-sn COMMAND [ARGS]...
```

The following interfaces must be available:

```console
ehp-sn --help
ehp-sn --version
ehp-sn COMMAND --help
ehp-sn COMMAND OPERATION --help
ehp-sn --install-completion
ehp-sn --show-completion
```

Help and completion may be generated by Typer, but their observable command names, arguments, options, defaults, and descriptions must agree with these CLI modules.

## Commands

| Command                   | Purpose                                                         | Status      |
| ------------------------- | --------------------------------------------------------------- | ----------- |
| [`data`](data.md)         | Generate and inspect immutable interim substrates               | Specified   |
| [`tasks`](tasks.md)       | Build and inspect processed task corpora                        | Specified   |
| [`train`](train.md)       | Plan, validate, and execute training                            | Specified   |
| [`evaluate`](evaluate.md) | Plan, validate, and execute evaluation                          | Specified   |
| [`analyze`](analyze.md)   | Derive scientific analyses and figures from committed artifacts | Specified   |
| [`report`](report.md)     | Package existing results for presentation or export             | Provisional |

## Command form

```console
ehp-sn COMMAND OPERATION [TARGET] [OPTIONS]
```

The shared operation names are:

| Operation  | Meaning                                                      |
| ---------- | ------------------------------------------------------------ |
| `list`     | List available definitions                                   |
| `show`     | Describe one definition                                      |
| `plan`     | Resolve configuration and intended actions without executing |
| `validate` | Check configuration, compatibility, or an existing artifact  |
| `build`    | Materialize an immutable data-like artifact                  |
| `run`      | Execute training, evaluation, or analysis                    |
| `inspect`  | Read an existing artifact without modifying it               |

Not every command group implements every operation. `build` is used for materializing data-like resources; `run` is used for executing computational protocols.

`inspect` is always read-only and bounded by default, but its selectors depend on the artifact kind. Likewise, validation levels are domain-specific. Higher levels include the checks of lower levels unless the command module states otherwise.

## Public configuration boundary

EHP-SN owns the public CLI and configuration semantics. Hydra is the default composition backend, not the public command language.

The CLI therefore uses:

```console
--config PATH
--set KEY=VALUE
```

It does not expose Hydra's complete override DSL as a stable EHP-SN contract.

Configuration precedence is:

```text
package and schema defaults
    < workspace or experiment configuration
    < --config file
    < --set overrides
    < dedicated invocation options
```

A dedicated invocation option such as `--device` overrides the corresponding execution field because its meaning is explicitly owned by that command.

### `--set` grammar

`--set` applies one repeatable dot-path override:

```console
--set protocol.training.max_steps=50000
--set optimizer.lr=0.0001
--set execution.deterministic=true
--set analysis.case_ids='["case-01", "case-02"]'
```

Rules:

- the key is a dot-separated path into the selected typed configuration;
- the key must already exist unless the command explicitly supports extension fields;
- values use TOML value syntax for strings, booleans, integers, floats, arrays, inline tables, and date/time values;
- clearing an optional configuration field is not supported by the initial CLI; a dedicated mechanism such as `--unset KEY` may be introduced only after a concrete workflow requires it and its schema and provenance semantics are specified;
- the parsed value must validate against the target field type;
- unknown keys, ambiguous paths, and type-invalid values are rejected;
- every accepted override and its source are recorded in the resolved request and artifact provenance.

Scientific parameters belong in version-controlled configuration or explicit recorded overrides. Hydra-specific syntax such as `++key=value`, Defaults List mutation, sweeps, and deletion operators is not part of the stable CLI contract.

## Shared option conventions

Only `--help`, `--version`, `--install-completion`, and `--show-completion` are root-level interfaces.

The following options are operation-local. They appear after the selected command and operation, as shown in the command modules:

| Option                | Default                      | Used by                                                              |
| --------------------- | ---------------------------- | -------------------------------------------------------------------- |
| `--format text\|json` | `text`                       | Operations that emit structured terminal output                      |
| `--quiet`             | Disabled                     | Emit only final results and errors                                   |
| `--verbose`           | Disabled                     | Emit normal output plus resolution details and progress information  |
| `--debug`             | Disabled                     | Emit verbose output plus diagnostic context and Python tracebacks    |
| `--no-color`          | Color enabled when supported | Disable terminal color and styling                                   |
| `--config PATH`       | Domain-specific              | Operations that resolve configuration                                |
| `--set KEY=VALUE`     | None                         | Operations that accept typed overrides                               |
| `--output PATH`       | Domain-specific              | Artifact-producing operations                                        |
| `--seed INT`          | Domain-specific              | Data generation, training, or evaluation according to seed ownership |
| `--device DEVICE`     | `auto` where supported       | Compute-execution operations                                         |
| `--precision POLICY`  | Domain-specific              | Compute-execution operations                                         |

The same spelling has the same meaning where it is supported, but an option is not automatically valid for every command.

`--quiet`, `--verbose`, and `--debug` are mutually exclusive output modes. Supplying more than one is a CLI usage error.

```text
normal   default informational output
quiet    final result and errors only
verbose  normal output plus resolution and progress details
debug    verbose output plus diagnostic context and tracebacks
```

Operations that expose `--quiet` suppress progress bars and non-essential telemetry while preserving errors and the final result.

## Proposed environment variables

Environment variables are reserved for execution and deployment concerns, not as a generic replacement for scientific configuration. The names below are proposed and do not become stable public API until required and verified by an implementation.

The proposed variables are:

| Variable               | Meaning                                                               |
| ---------------------- | --------------------------------------------------------------------- |
| `EHP_SN_CACHE_DIR`     | Local cache root                                                      |
| `EHP_SN_ARTIFACT_ROOT` | Default artifact root when no more specific destination is configured |
| `EHP_SN_TRACKING_URI`  | Optional tracking backend URI                                         |
| `EHP_SN_DEBUG`         | Enable debug diagnostics when set to a truthy value                   |

Command-line options override these values. Scientific task, model, protocol, dataset, and seed configuration must not be silently sourced from arbitrary `EHP_SN_*` variable names.

A proposed environment variable becomes stable only after its ownership, precedence, serialization behavior, and use in subprocess or distributed execution are covered by CLI acceptance tests.

## Experiment references

Training and evaluation operate on the same experiment definitions:

```text
experiment:arena-tem/v1
experiment:goaltrace-hrm/v1
```

Where the expected reference kind is unambiguous, the shorter form may be accepted:

```text
arena-tem/v1
```

The CLI must not maintain separate public training and evaluation recipe catalogues for the same scientific experiment.

## Artifact and checkpoint references

Commands accept either canonical logical references or filesystem paths where the relevant argument permits them.

Canonical logical forms are:

```text
artifact:<logical-id>
checkpoint:<logical-id>
```

Filesystem forms are:

```text
./relative/path
/absolute/path
```

Resolution rules:

1. A value beginning with a recognized kind prefix, such as `artifact:` or `checkpoint:`, is resolved only as that logical reference kind.
2. Any other value is treated as a filesystem path when the command permits paths.
3. A path and a logical reference never compete for precedence because the prefix makes the intended form explicit.
4. A command that prints a logical artifact or checkpoint reference must emit a value accepted unchanged by downstream commands.
5. Logical references may be resolved by local or configured persistence adapters. Their manifests or content digests, not machine-specific physical paths, determine identity.
6. Filesystem paths are invocation locations and are recorded in provenance; they are not assumed to remain portable across machines.

Malformed or unknown logical references are resolution errors. A well-formed reference that resolves to a known identity but whose payload is unavailable on the current machine is a planning warning and a resource-validation error.

## Artifact identity, placement, and reuse

Commands that publish artifacts use:

```text
resolve → validate → stage → validate staged output → atomic commit
```

A committed immutable artifact is never overwritten in place.

The logical or scientific artifact identity is distinct from its physical output location. Changing only `--output` does not change scientific content identity unless the relevant artifact contract explicitly says otherwise. The selected location is always recorded in invocation provenance.

Reuse is command-specific:

- `data build` and `tasks build` may reuse an identical committed artifact because their contracts are content-addressed and idempotent.
- `analyze run` may reuse an equivalent result only when the selected analysis declares deterministic, idempotent identity semantics.
- `train run` creates a new run unless it explicitly resumes an existing lineage or a future deduplication policy is requested.
- `evaluate run` follows the evaluation identity policy documented by the selected regime and request; reuse is never assumed merely because the output path exists.
- `report` remains provisional.

For commands that permit reuse:

- matching identity and content fingerprint may reuse the existing committed artifact;
- matching identity with a different content fingerprint is an output conflict and requires a new version or identity;
- `--replace-incomplete` may remove only incomplete, failed, or uncommitted state. It never replaces a committed valid artifact.

`--overwrite` is reserved for replaceable presentation projections such as provisional report packages and exports. `--replace-incomplete` applies only to failed or uncommitted staging state for authoritative artifacts.

## Planning and validation boundary

`plan` resolves definitions, identities, effective configuration, intended inputs, destinations, and actions. It may report unavailable resources as warnings, but it does not require all runtime resources to be readable unless the command module explicitly says otherwise.

Resource-level `validate` requires the relevant inputs, devices, checkpoints, and destinations to exist and satisfy their contracts. Execution-level validation may additionally construct minimal runtime objects.

A plan describes only the exact request arguments used to create it. Changing `--output` or any other request option produces a different request and invalidates assumptions derived from the earlier plan.

## Machine-readable output

Commands that return structured information support:

```console
--format json
```

Successful JSON output contains a `status` field and the command-specific result. Failed JSON output contains at least:

```json
{
  "status": "error",
  "code": "evaluate.checkpoint.not_found",
  "message": "Checkpoint does not exist: runs/arena-tem/best.ckpt"
}
```

The string `code` identifies the domain-specific failure. The process exit code identifies the broad failure category.

## Exit codes

|  Code | Meaning                                    |
| ----: | ------------------------------------------ |
|   `0` | Success                                    |
|   `1` | Unexpected internal or operational failure |
|   `2` | Invalid CLI usage                          |
|   `3` | Invalid configuration or specification     |
|   `4` | Referenced input not found or unreadable   |
|   `5` | Validation or compatibility failure        |
|   `6` | Execution failure                          |
|   `7` | Artifact commit or publication failure     |
|   `8` | Existing output conflict                   |
| `130` | Interrupted by the user                    |

These codes are a proposed stable contract until verified by CLI acceptance tests.

## Example lifecycle

```console
ehp-sn data build openfield \
    --config config/data/openfield/default.toml

ehp-sn tasks build arena \
    --config config/tasks/arena/default.toml

ehp-sn train run experiment:arena-tem/v1 \
    --seed 42

ehp-sn evaluate run experiment:arena-tem/v1 \
    --checkpoint runs/arena-tem/checkpoints/best.ckpt \
    --regime test
```

The exact logical artifact or checkpoint references printed by one command must be accepted unchanged by downstream commands that consume them.
